# tabora-server

Сервер аккаунтов Tabora: вход, устройства, ящик `имя@tabora.app` и алиасы, синхронизация данных
браузера между устройствами и обращения в поддержку. Один статический исполняемый файл (Rust),
PostgreSQL, почтовый сервер Stalwart по JMAP на том же хосте.

## Что сервер знает и чего не знает

- Пароль он не получает. Браузер выводит из пароля хеш входа (Argon2id 64 МБ, затем HMAC) и
  присылает его; в базе лежит только HMAC от этого хеша с солью пользователя и секретом сервера.
  Ключ сейфа браузер выводит отдельно, на сервер он не уходит.
- Сброс забытого пароля требует подписи ключом восстановления (Ed25519, у сервера только открытая
  половина), свежего одноразового nonce; после сброса все устройства выходят из аккаунта.
- Основной пароль ящика выводится из секрета сервера и номера пользователя, нигде не хранится и
  клиентам не отдаётся. Каждое устройство получает свой пароль приложения (IMAP и SMTP), он
  отзывается при выходе с устройства.
- Адрес удалённого алиаса никому не выдаётся повторно: иначе новый владелец получал бы письма
  прежнего.
- Двухфакторная защита входа: коды приложения (TOTP, RFC 6238) и десять одноразовых резервных
  кодов. Секрет в базе зашифрован ключом сервера (AES-256-GCM, привязан к пользователю), от
  резервных кодов там только HMAC. Код приложения принимается один раз.
- Резервный адрес нужен для сброса забытого пароля кодом из письма. Такой сброс доказывает только
  доступ к резервному ящику, поэтому второй фактор при нём остаётся обязательным. Сервер меняет лишь
  пароль аккаунта: ключа сейфа у него нет, сейф на компьютере пользователь открывает сам. Сброс
  ключом восстановления, наоборот, снимает двухфакторную защиту: это главный запасной вход.
- Письма сервера (коды, уведомления о переменах во входе) уходят от ящика `no-reply@домен`
  обычными вызовами JMAP по локальному адресу. Ящик создаётся при первом письме.
- Данные синхронизации сервер прочитать не может: каждую запись браузер шифрует ключом, которого
  у сервера нет. Сервер видит только раздел и ключ записи, её размер, время и порядок изменений
  и отпечаток ключа шифрования (16 знаков hex).
- Обращения в поддержку, наоборот, хранятся открыто: переписку и вложения читает поддержка,
  сквозного шифрования здесь нет. Обращение видят только его автор и сотрудники поддержки.

## Интерфейс

Контракт аккаунта задан браузером: `src/browser/base/content/tabora/account/Account.sys.mjs`,
класс `HttpBackend`. Дополнения сервера:

| Запрос | Ответ |
|---|---|
| `POST /v1/account/register`, `/login` | к ответу добавлено `mail: { address, login, password, imap, smtp }` — пароль приложения этого устройства (или `null`, если почтовый сервер не ответил) |
| `POST /v1/mail/password` (Bearer) | `{ mail }` — новый пароль приложения устройства, прежний перестаёт действовать |
| `GET /v1/mail/aliases` (Bearer) | `[{ id, address, site, space, by, on, created }]` |
| `POST /v1/mail/aliases { site?, space?, by? }` | новый алиас вида `booking-k3f9@tabora.app` |
| `PATCH /v1/mail/aliases/:id { on?, site?, space? }` | выключенный алиас отвечает отправителю «ящика нет» |
| `DELETE /v1/mail/aliases/:id` | алиас перестаёт принимать почту навсегда |
| `GET /v1/health` | `{ ok, mail }` |
| `POST /v1/account/register`, `/login`, `/reset/email/confirm` с `mailAccess: "session"` | доступ к почте по сессии (веб-версия): пароль приложения не выдаётся, в ответе `mail: { address, session: true }`; прежний пароль приложения устройства отзывается |
| `GET /v1/mail/jmap/session` (Bearer) | описание ящика от почтового сервера (номер учётки, пределы) |
| `POST /v1/mail/jmap { using, methodCalls }` | вызовы JMAP от имени владельца ящика; только почтовые возможности и методы (`Mailbox/*`, `Thread/*`, `Email/*`, `SearchSnippet/get`, `Identity/*`, `EmailSubmission/get\|set`), иначе `403 mail-forbidden`; тело до 4 МиБ, до 32 вызовов |
| `GET /v1/mail/jmap/download/:account/:blob/:name?accept=тип` | содержимое вложения или письма: `Content-Disposition: attachment`, `nosniff`, без кэша |
| `POST /v1/mail/jmap/upload/:account` | загрузить вложение или исходник письма (до 52 МиБ): `{ accountId, blobId, type, size }` |
| `GET /v1/account/devices` (Bearer) | `[{ id, name, at, current, active }]` — `active`: у устройства есть действующая сессия |
| `POST /v1/account/devices/:id/revoke { loginHash }` | сеанс другого устройства завершён: его сессии удалены, пароль приложения почты отозван, устройство убрано из списка; своё устройство — `400`, неизвестное — `404 not-found` |
| `POST /v1/account/login { …, totp? }` | при включённой защите без кода — `401 2fa-required`, с неверным — `401 bad-2fa`; `totp` — код приложения или резервный код |
| `GET /v1/account/security` (Bearer) | `{ mail, twoFactor: { enabled, since, backupCodes }, backupEmail: { address, since }?, backupEmailPending: { address, expiresAt }?, recoveryKey }` |
| `POST /v1/account/2fa/setup { loginHash }` | `{ secret, uri }` — секрет ждёт первого кода 15 минут, защита ещё выключена |
| `POST /v1/account/2fa/enable { code }` | `{ backupCodes: [10] }` — показываются один раз |
| `POST /v1/account/2fa/disable { loginHash, code }` | защита выключена, резервные коды удалены |
| `POST /v1/account/2fa/codes { loginHash, code }` | `{ backupCodes }` — прежние перестают действовать |
| `POST /v1/account/backup-email { loginHash, code?, address }` | на адрес уходит код из шести цифр; `{ pending: { address, expiresAt } }` |
| `POST /v1/account/backup-email/verify { code }` | `{ address }` — адрес стал резервным |
| `POST /v1/account/backup-email/remove { loginHash, code? }` | адрес удалён |
| `POST /v1/account/reset/email { email }` | всегда `{}`; если у аккаунта есть резервный адрес, на него уходит код из восьми цифр |
| `POST /v1/account/reset/email/confirm { email, code, newLoginHash, kdf, totp?, deviceId?, deviceName? }` | пароль сменён, все сессии завершены; устройству, назвавшему себя, сразу выдаётся сессия (`{ userId, session, kdf, mail }`) |
| `POST /v1/account/reset` (ключ восстановления) | в ответе `twoFactorDisabled` |
| `GET /v1/mail/pgp` (Bearer) | `{ rev, fingerprint, publicKey, blob, wrapPassword, wrapRecovery, updatedAt }` — ключ шифрования почты: открытый ключ, зашифрованная браузером копия закрытого и обёртки ключа данных (Base64, чего нет — `null`) |
| `PUT /v1/mail/pgp { rev, fingerprint?, publicKey?, blob?, wrapPassword?, wrapRecovery?, replace?, loginHash? }` | то же после изменения; `409 pgp-conflict` — запись изменилась или у аккаунта уже другой ключ; `wrapPassword` и `replace` требуют `loginHash` |
| `GET /.well-known/openpgpkey/hu/<хеш>?l=<имя>` | открытый ключ адреса двоичным (Web Key Directory) или 404; `…/policy` — пустой файл политики |
| `GET /v1/sync?since=<rev>&limit=<n>` (Bearer) | `{ rev, gen, keyId, items: [{ c, id, rev, deleted, blob }], more }` — записи новее `since` по возрастанию `rev`; `limit` по умолчанию 500, не больше 1000 |
| `POST /v1/sync { gen, keyId, items: [{ c, id, base, blob?, deleted? }] }` | `{ rev, gen, keyId, saved: [{ c, id, rev }], conflicts: [{ c, id, rev, deleted, blob }] }`; `409 sync-key`, `409 sync-reset` — с полями `gen` и `keyId` |
| `POST /v1/sync/reset { keyId }` | `{ rev, gen, keyId }` — записи удалены, поколение выросло, ключ новый |
| `DELETE /v1/sync` | `{ rev, gen, keyId: null }` — синхронизация выключена, данные стёрты |
| `GET /v1/support/tickets?scope=mine\|all&status=open\|answered\|closed` (Bearer) | `{ staff, tickets: [{ id, subject, status, createdAt, updatedAt, messages, unread, author? }] }` — до 200, недавно изменённые сверху; `scope=all` и `author` — только сотруднику |
| `POST /v1/support/tickets { subject, text, meta?, files? }` | новое обращение в том же виде, что при чтении |
| `GET /v1/support/tickets/:id` | `{ id, subject, status, createdAt, updatedAt, staff, author?, meta?, messages: [{ id, from, text, at, files: [{ id, name, type, size }] }] }`; чтение отмечает обращение прочитанным |
| `POST /v1/support/tickets/:id/messages { text, files? }` | обращение целиком; сообщение автора → `open`, ответ поддержки → `answered` |
| `POST /v1/support/tickets/:id/status { status: "closed" \| "open" }` | обращение целиком |
| `GET /v1/support/files/:id` | байты вложения: `Content-Type` вложения, `Content-Disposition: attachment`, `nosniff`, `Cache-Control: private, max-age=3600` |
| `GET /v1/support/unread` | `{ count, staff, queue? }` — свои обращения с непрочитанным ответом; `queue` (сотруднику) — обращения всех в статусе `open` |

`loginHash` в настройках входа — повторная проверка пароля; `code` — второй фактор, обязателен,
если защита включена.

Почта веб-версии (`src/webmail.rs`). Браузер ходит на почтовый сервер сам, с паролем приложения
устройства; веб-странице это не подходит: паролей приложений у ящика считаные штуки (предел
почтового сервера — пять), а закрытая вкладка держала бы свой до истечения сессии. Поэтому
веб-версия работает с ящиком через этот сервер по токену сессии: в браузере нет почтового пароля,
выход или завершение сеанса сразу закрывает и почту, а из методов доступны только почтовые —
настройки ящика и пароли приложений через этот путь недоступны. Запросы пересылаются почтовому
серверу от имени владельца ящика (основной пароль ящика, вход только с 127.0.0.1); отказ в методе
до почтового сервера не доходит. Предел — 1500 запросов в минуту на пользователя. Проверки:
`tests/webmail.mjs` с имитацией почтового сервера `tests/fake-jmap.mjs`.

Ключи почты (`src/pgp.rs`). Закрытый ключ приходит уже зашифрованным: браузер шифрует его случайным
ключом данных, а ключ данных — ключом из пароля (тот же тяжёлый KDF, что у хеша входа, другая
метка) и, отдельно, ключом из ключа восстановления. Сервер не может прочитать копию и не
проверяет её содержимое; блоки дополнительно запечатаны ключом сервера, чтобы утечка одной базы
не дала материала для подбора пароля. Открытый ключ проверяется (это пакет открытого ключа
OpenPGP, отпечаток ключа версии 4 пересчитывается) и публикуется в каталоге. Первый ключ аккаунта
создаётся по сессии; замена ключа и обёртка паролем — только с хешем входа. Каталог на
основном домене отдаёт nginx (`infra/nginx/tabora.app.conf`), браузер ходит за ключами адресатов
Tabora на тот же путь сервера аккаунтов.

Синхронизация (`src/sync.rs`). Запись — это раздел `c` (`^[a-z]{1,16}$`), ключ `id`
(`^[A-Za-z0-9_-]{1,64}$`) и блок `blob` (Base64, после декодирования от 1 байта до 96 КиБ),
зашифрованный браузером. У пользователя один счётчик изменений `rev`: каждая сохранённая запись
получает следующий номер, и устройство забирает всё, что новее номера, который оно уже видело.
Запись сохраняется, только если `base` равен её `rev` на сервере (0 — записи ещё нет); иначе она
попадает в `conflicts` с тем, что лежит на сервере, а остальные записи запроса сохраняются.
Если устройство ссылается на запись, которой на сервере нет, в `conflicts` она приходит как
удалённая: `rev: 0, deleted: true, blob: null`. `deleted: true` оставляет надгробие без блока.
Записи разбираются по порядку, поэтому повтор ключа в одном запросе сверяется уже с только что
сохранённой версией. `gen` — поколение данных: оно растёт при сбросе и при `DELETE`, запрос со
старым поколением получает `409 sync-reset`. `keyId` (`^[0-9a-f]{16}$`) запоминается при первой
записи; другой ключ — `409 sync-key`. При обоих отказах ничего не сохраняется, а в теле ошибки,
кроме `code` и `message`, приходят текущие `gen` и `keyId`. Счётчик `rev` не уменьшается никогда:
сброс прибавляет к нему единицу, `DELETE` его не меняет.

Чтение отдаёт не больше `limit` записей и не больше 8 МиБ блоков за один ответ (первая запись
входит всегда); если осталось ещё, `more: true`, и клиент повторяет запрос с `since`, равным
`rev` последней полученной записи. Пределы записи: тело запроса до 4 МиБ, до 200 записей в
запросе, не больше 30 000 записей на пользователя вместе с надгробиями и 64 МиБ блоков
(надгробия в объём не входят) — `413 sync-limit`, запрос отклоняется целиком; запросу, который
места не прибавляет (обновление на меньший блок, удаление), предел не мешает. Неверная форма —
`400 sync-invalid`.

Обращения в поддержку (`src/support.rs`). `subject` — 3–140 знаков, `text` — 1–8000; `meta` —
объект JSON до 2 КиБ (версия браузера, система: его присылает клиент, видит только поддержка);
`files` — до четырёх вложений `{ name, type, data }`: `type` — `image/png`, `image/jpeg`,
`image/webp` или `text/plain`, `data` — Base64, от 1 байта до 2 МиБ; из имени убираются `/`, `\`
и управляющие знаки, оно обрезается до 120 знаков. Содержимое вложения с заявленным типом не
сверяется: вложения отдаются только как файлы для сохранения и с запретом угадывать тип. Тело
запроса с вложениями — до 12 МиБ (больше — `400 support-invalid`).

Статусы: `open` — ждёт поддержку, `answered` — поддержка ответила, `closed`. Сотрудники — аккаунты
с адресами из `TABORA_SUPPORT_STAFF`; сотрудник в чужом обращении действует как поддержка
(в ответе `staff: true`, видны `author` и `meta`, его сообщения идут `from: "staff"`), в своём
собственном — как обычный пользователь (`staff: false`). Постороннему чужое обращение и его
вложения отвечают `404 not-found`. `unread` — есть сообщения другой стороны новее отметки
прочтения; отметку ставит чтение обращения и собственное сообщение. Письма: о новом обращении
и об ответах пользователя — на `TABORA_SUPPORT_NOTIFY`, об ответе поддержки — автору на адрес
его аккаунта; письма уходят в фоне, и сбой почты ничего не отменяет.

Настройки поддержки: `TABORA_SUPPORT_STAFF` — адреса аккаунтов сотрудников через запятую (регистр
не важен; пусто — сотрудников нет), `TABORA_SUPPORT_NOTIFY` — адрес для писем о новых обращениях
и ответах пользователей (пусто — такие письма не уходят). В списке сотрудников должны стоять
только адреса уже существующих аккаунтов: сотрудником становится тот, кто владеет аккаунтом с
таким адресом, и свободное имя из списка мог бы занять кто угодно.

Ошибки — `{ code, message }`; `message` на русском и показывается пользователю как есть.
Коды: `bad-credentials`, `session-expired`, `rate-limited`, `taken`, `bad-nonce`, `bad-proof`,
`no-recovery`, `mail-unavailable`, `signup-closed`, `signup-paused`, `alias-limit`, `old-client`,
`2fa-required`, `bad-2fa`, `2fa-on`, `2fa-off`, `2fa-setup-expired`, `bad-address`, `same-address`,
`bad-code`, `no-code`, `sync-invalid`, `sync-limit`, `sync-key`, `sync-reset`, `mail-forbidden`, `support-invalid`,
`support-limit`, `not-found`.

## Ограничения

Вход: пять неверных паролей подряд для пары «адрес + IP» — пауза минута, дальше удвоение до часа
(по адресу аккаунта целиком блокировки нет, иначе владельца можно было бы отрезать чужими
попытками). Регистрация: три аккаунта в сутки с одного IP и общий суточный предел
(`TABORA_SIGNUP_DAILY_CAP`, по умолчанию 50); `TABORA_SIGNUP=closed` закрывает её совсем.
Счётчики живут в памяти процесса.

Второй фактор: пять неверных кодов подряд — пауза 15 минут, дальше удвоение до суток; счёт идёт
по аккаунту, а не по адресу клиента, и хранится в базе (шесть цифр перебираются дёшево, и
перезапуск сервера не должен обнулять паузу). Коды из писем: пять попыток на код, срок 30 минут,
новый код заменяет прежний. Письма: код сброса — не больше трёх в сутки на аккаунт и пяти
запросов в час с адреса, подтверждение резервного адреса — три в час и восемь в сутки на
аккаунт, всего писем от сервера — `TABORA_MAIL_DAILY_CAP` в сутки (по умолчанию 500).

Синхронизация: 600 чтений и 600 записей в час на пользователя, сброс — не больше шести в час,
`DELETE` — тридцати. Обращения: не больше пяти незакрытых у пользователя и десяти новых в сутки,
не больше 200 сообщений в обращении и 60 сообщений в час от пользователя (`429 support-limit`).
Письма поддержке ограничены отдельно — двенадцать в час из-за одного пользователя и половина
суточного предела писем сервера на всех: обращениями нельзя выбрать запас, из которого уходят
коды сброса пароля. Сообщение сохраняется и тогда, когда письмо о нём не ушло.

## Сборка, проверка, выкладка

```sh
cargo test                                   # модульные тесты
# контракт на запущенном экземпляре без почты и с пустой базой:
TABORA_DOMAIN=tabora.app TABORA_LISTEN=127.0.0.1:7711 TABORA_DB=postgres://… \
  APP_SIGNING_KEY=$(openssl rand -hex 32) TABORA_SIGNUP_PER_IP=6 TABORA_MAIL_OUTBOX=/tmp/tabora-outbox \
  TABORA_SUPPORT_STAFF=kot.test@tabora.app TABORA_SUPPORT_NOTIFY=postmaster@tabora.app cargo run &
node tests/contract.mjs http://127.0.0.1:7711 tabora.app /tmp/tabora-outbox kot.test@tabora.app postmaster@tabora.app
infra/deploy.sh server                       # сборка под Linux (musl) с этой машины и установка
infra/deploy.sh nginx                        # настройки nginx (каталог ключей на основном домене)
```

Контрактная проверка сама регистрирует аккаунт сотрудника поддержки: его адрес — четвёртый
аргумент (по умолчанию `kot.test@<домен>`), и он же должен стоять в `TABORA_SUPPORT_STAFF`
запущенного сервера; пятый аргумент (по умолчанию `postmaster@<домен>`) — адрес из
`TABORA_SUPPORT_NOTIFY`, на нём проверяются письма поддержке. Проверка пределов синхронизации
загружает на сервер около 80 МиБ.

Для сборки под сервер нужна цель `rustup target add x86_64-unknown-linux-musl`; зависимости
только на Rust, линкер берётся из поставки Rust (`.cargo/config.toml`). Настройки — переменные
окружения, список в начале `src/main.rs`; на сервере они лежат в `/etc/tabora/server.env`.
